**[HIGH — Story 5.3] Baserow `date__before` filter so sánh DATE only, không phải timestamp**

Amelia (Developer): "MC-Relay-Watchdog query: `filter__created_at__date__before={{ sla_cutoff }}` — Baserow `date__before` operator so sánh chỉ phần DATE (YYYY-MM-DD), không phải full ISO-8601 timestamp. Nếu case tạo lúc 9:00 sáng và watchdog chạy lúc 10:00 sáng cùng ngày, filter trả về 0 rows vì '2026-06-07' không phải 'before 2026-06-07'."

Winston (Architect): "Fix: xóa URL filter `date__before`. Query TẤT CẢ rows với `state=waiting_pharmacist`. Thêm JavaScript timestamp comparison trong Code node 'Expand Overdue Cases': `new Date(row.created_at).getTime() < new Date(cutoff).getTime()`. JS millisecond comparison chính xác, không bị date-only truncation."

Mary (Analyst): "Lesson: Baserow `date` operators (date__before, date__after, date__equal) hoạt động trên DATE portion. Temporal filters với sub-day precision PHẢI được xử lý ở JavaScript layer. Pattern này khác với Epic 4's $json context reset — runtime behavior của Baserow API, không phải n8n."

### 💡 Key Insights

1. **Baserow `date` operators compare DATE only, not timestamp.** `filter__created_at__date__before` truncates to YYYY-MM-DD. Sub-day temporal filters PHẢI thực hiện trong JavaScript millisecond comparison sau khi fetch rows. Pattern: fetch all → JS filter → process.

2. **`create_escalation_case` trả về case_id, không phải Baserow row_id.** Bất kỳ workflow nào cần PATCH EscalationCase row phải: GET list filtered by case_id → extract `results[0].id` (Baserow auto-int) → dùng cho PATCH URL. Không thể skip GET step.

3. **MC-Handle-InboundReply là long-lived single workflow.** 51 nodes sau Epic 5. Pattern đã stable — Epic 6 không extend thêm. Refactor thành sub-workflows là option sau go-live nếu team thêm epic có inbound handling.

4. **Emergency 115 path là parallel, không sequential.** Send 115 ngay lập tức + create EscalationCase cùng lúc — không depend nhau. Pattern: Guard: Is Emergency → true branch gửi 115 → sau đó MERGE hoặc continue sang Create Escalation Case. Patient safety không bao giờ wait on business logic.

5. **Pharmacist reply detection bằng regex case_id.** Dược sĩ reply tin Zalo bình thường nhưng bao gồm ESC-format mã ca → hệ thống detect và xử lý. Không cần dedicated pharmacist channel — tận dụng Zalo channel hiện có.

6. **Audit-first pattern scale tốt cho relay path.** 3 send paths mới trong relay flow đều follow pattern từ Epic 4 nodes 17/19: write pending → send → patch status. 0 deviation. Pattern proven stable.

7. **OpenClaw plugin + guardrail format đã proven.** faq-guardrail.yml + trigger-guardrail.yml cùng format. Future guardrails có template để follow. Không cần invent format mới.

8. **is_complaint_active là cross-cutting escalation gate.** Khi true: bypass FAQ, tạo complaint_serious escalation. Pattern nhất quán qua Stories 5.1, 5.2. Epic 6 không thay đổi behavior này.

**Discovery 3: NFR-2 guardrail scope phải check OUTPUT, không INPUT**

Winston (Architect): "Story 5.1 HIGH finding: guardrail ban đầu scan input message (câu hỏi của khách). **Key Takeaways Epic 5:**

1. **Baserow date operators are DATE-only.** `date__before`, `date__after`, `date__equal` compare YYYY-MM-DD. Sub-day temporal filtering always requires JavaScript timestamp comparison post-fetch. Apply to any time-sensitive watchdog or cron query.

2. **create_escalation_case returns case_id, not row_id.** Two-step pattern required for PATCH: GET list (filter case_id) → extract results[0].id → PATCH with integer id. Document in every story that needs EscalationCase update.

3. **NFR-2 guardrail must check OUTPUT, not INPUT.** Medical safety guardrail scanning input creates false positive rejections for legitimate patient questions. Guardrail scope = answer validation, not question validation.

4. **Emergency 115 is parallel, not sequential.** Patient safety send is independent of escalation case creation. Never gate emergency notification on business logic success.

5. **Audit-first pattern proven at scale.** 3 new relay send paths, all following nodes 17/19 pattern from Epic 4. Zero deviation. Pattern stable — apply to any future Zalo send operation.

6. **MC-Handle-InboundReply is at natural growth limit.** 51 nodes adequate for current feature set. Future inbound features should consider sub-workflow decomposition (e.g., MC-Handle-PharmacistReply) rather than extending the main workflow.

7. **Pharmacist reply via regex mã ca works.** No dedicated channel needed — pharmacist replies in normal Zalo thread with ESC-format case ID. Simple operational instruction, zero infrastructure cost.

8. **Epic 6 is read-only.** CRM/Dashboard does not extend inbound flow. Epic 6 builds on existing Baserow data — no new n8n webhook handlers, no new OpenClaw tools. Risk profile is significantly lower than Epic 5.
